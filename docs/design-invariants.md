# Design invariants

The load-bearing engineering rules behind ClipMenu's clipboard, menu, and storage
code. Source comments cite these sections **by name** — for example
`(design-invariants.md — History bound)` — so a citation can't silently rot when
a section moves.

Each rule is here because breaking it caused, or would cause, a real defect. This
is the *how*, not the *what*: product behavior lives in the README and
`WhatsNewConfig.swift`.

> Cite sections by name, never by number. This file replaced an internal
> `app/CLAUDE.md` that used numbered sections; the numbers drifted out of sync
> with the prose and several citations ended up pointing at the wrong section.

## Clipboard polling

macOS has **no clipboard-change notification**, so capture polls
`NSPasteboard.general.changeCount`.

- The poll loop runs **off the main actor** — `PasteboardMonitor` is an `actor`,
  and both the `changeCount` read and the payload snapshot happen on its
  executor. Copying a multi-MB image or PDF must never stall the UI.
- Read pasteboard payloads **only when `changeCount` actually changed**, never on
  every tick.
- Interval: default **0.75s**, clamped to **0.25s–1.0s**
  (`PasteboardMonitor.effectiveInterval`). The 0.25s floor stops a `0` from the
  preferences slider turning the poll into a busy loop; the 1.0s ceiling mirrors
  legacy `MAX_TIME_INTERVAL`. Wake-up tolerance is a quarter of the interval so
  the OS can coalesce our recurring wake with other timers.
- `NSPasteboard` is not `Sendable`. Each read obtains `NSPasteboard.general`
  locally and never sends it across an isolation boundary — only the `Sendable`
  `PasteboardSnapshot` crosses actors.
- Apply the exclusion and privacy rules **before** recording: the frontmost-app
  exclude list, the per-type store toggles, and the
  [nspasteboard.org](https://nspasteboard.org) markers
  (`ConcealedType` / `TransientType` / `AutoGeneratedType`) that password
  managers use to opt a write out of clipboard history.
- De-duplicate by stable content hash. The hash must be stable **across
  launches** (`stableContentHash` is FNV-1a, not `Hasher`), because de-dup is
  persisted.

## History bound

The user's configured history cap is a hard bound on what is materialized
anywhere — on disk and in view.

- **`ClipStore.maxHistorySize` is the single source of truth.** Storage (`trim`),
  the menu, the History-menu search, `Export…`, and the upgrade migration all go
  through it, so the on-disk and in-view history can never disagree.
- **The cap is clamped to a minimum of 1.** This is not cosmetic. The cap is used
  raw as a Core Data `fetchLimit` *and* `fetchOffset`, where `0` does not mean
  "none":
  - `fetchLimit = 0` means **no limit** — the menu would show the entire store.
  - `fetchOffset = 0` selects **every row**, so `trim()` would delete the whole
    history on the next capture, including the clip just inserted.
  - A negative offset makes the fetch **throw**, and because `trim()` uses
    `try?` the error is swallowed and trimming silently stops forever.

  A preference value of `0` therefore used to destroy the user's entire history
  silently, and a negative one disabled the bound. Clip history is a regenerable
  cache that is **not** covered by the backup feature, so that loss was
  unrecoverable. Never pass an unclamped preference into a fetch descriptor.
- `boundedHistoryDescriptor` and `trimOverflowDescriptor` are **symmetric**: what
  one keeps, the other deletes. Change them together.
- Persist a new clip **before** trimming. An unsaved, pending insert is not
  ordered by an offset fetch the way a saved row is, so trimming first lets a
  full history pick the just-inserted clip as the "overflow" and delete it —
  silently dropping every new copy once the store fills up.
- `trim()` fetches only the overflow (offset past the cap), never the whole
  sorted history, so it stays cheap under rapid copies. It also handles the user
  *lowering* the cap: the offset fetch then returns everything beyond the new,
  smaller cap.
- Filter searches **in the store**, not by fetching every row and filtering in
  Swift on each keystroke.

## Images and memory

Never keep full-size images alive to draw a menu.

- At capture, generate a downsampled PNG thumbnail with
  `CGImageSourceCreateThumbnailAtIndex`
  (`kCGImageSourceCreateThumbnailFromImageAlways` +
  `kCGImageSourceThumbnailMaxPixelSize`), longest side
  `Thumbnailer.storedMaxPixelSize` (256 px, a few tens of KB). Store it on the
  clip row and render the menu from it.
- Keep the **original bytes byte-for-byte** so paste reproduces the exact
  clipboard content, in a **separate row** (`ClipImage`) behind a lazily-faulted
  relationship. Faulting a `ClipRecord` loads its whole row, so a large inline
  image column would be pulled in on every menu fetch.
- The one deliberate exception: when the user picks a thumbnail size needing more
  real pixels than the stored 256 px holds, `Thumbnailer` streams the **original**
  through ImageIO once to decode a crisp thumbnail rather than upscaling a blurry
  one. Even then the original is downsampled and released immediately — only the
  small result is cached.
- The stored thumbnail is **display-only**. It never goes back on the pasteboard.
- Bound every cache. Batch bulk work (the thumbnail backfill uses one short-lived
  `ModelContext` per image) so peak memory is one image, not the whole history.

## Paste synthesis and permissions

- To paste into the frontmost app: set `NSPasteboard.general`, then synthesize ⌘V
  with `CGEvent` (keycode `9` = V, `.maskCommand`) posted to `.cghidEventTap`.
- This needs **Accessibility (TCC) permission**. Check `AXIsProcessTrusted()` and
  prompt when untrusted — **never fail silently**.
- Global hotkey registration (`RegisterEventHotKey`) needs **no** TCC permission;
  only synthetic event *posting* does. A background agent can register hotkeys
  without prompting.
- Legacy did **not** restore the previous pasteboard after pasting, so neither do
  we: the selected clip stays on the pasteboard and re-sorts to the top via
  de-dup.
- The sandboxed Mac App Store build **cannot** post synthetic key events into
  other apps. Gate on the actual capability (`DistributionChannel`), not just a
  disabled toggle — the preference can arrive `true` via settings sync from a
  direct-build install.

## Persistence

- `ModelContainer` is `Sendable`; **`ModelContext` is not.** Do background writes
  through a `@ModelActor` (`ClipStore`) and never share a context across actors.
- Keep large binary payloads out of hot rows: `@Attribute(.externalStorage)` for
  RTF/PDF/image blobs, so SwiftData writes them as separate files and history rows
  stay small.
- Index the columns that every capture and menu open queries — de-dup looks up by
  `contentHash`, and the history always sorts by `lastUsedDate`/`createdDate`.
  Without them both are full scans that grow with the store.
- SwiftData adds `#Index` indexes to a **fresh** store but its lightweight
  migration does **not** add them to a store created before the index was
  declared. `HistoryIndexRepair` recreates exactly those indexes on an existing
  store before SwiftData opens it. Every step is best-effort: any failure leaves
  the store as-is.
- Snippets and history live in **separate stores** under one container. Snippets
  are user-authored and protected by folder-based backups; history is a
  regenerable cache. Treat them accordingly — a recovery path may reset the
  history store, but never destroy snippets.
- Preferences are `UserDefaults` only. Values arriving from the synced settings
  sidecar are **untrusted input**: validate or clamp before use (see
  [History bound](#history-bound)).
